You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
Soil Health Card (SHC - soil testing and advisory generation)
service on the UMANG app.

The number of tools should be sufficient (typically 10–14 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Soil sample registration
- Soil sample collection tracking
- Soil testing request submission
- Soil Health Card generation
- Nutrient analysis interpretation
- Fertilizer recommendation generation
- Soil improvement advisory
- Historical soil report tracking
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Sample-based system:
  Each Soil Health Card is generated from a specific soil sample.

- Land linkage:
  Soil sample must be linked to a valid land parcel.

- Lab dependency:
  Soil testing must be completed before report generation.

- Periodicity:
  Soil Health Cards are typically generated once every 2 years.

- Nutrient immutability:
  Lab-measured values (N, P, K, pH, etc.) cannot be modified.

- Recommendation dependency:
  Fertilizer recommendations MUST be derived from test results.

- Advisory limitation:
  Tools provide recommendations only — no execution of farming actions.

- Grievances should ONLY be raised after checking sample/report status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- sample_status:
  registered → collected → in_transit → under_testing → tested

- report_status:
  not_generated → generated → delivered

- advisory_status:
  not_available → generated → updated → obsolete

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- invalid or missing land parcel
- sample not collected but test requested
- lab testing delayed or stalled
- duplicate sample registration
- partial or missing nutrient values
- conflicting soil data across samples
- outdated soil reports used
- incorrect mapping of sample to farmer
- recommendation mismatch due to bad input

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (land linkage, sample ID validity)
- failure conditions (test not completed, report not generated)
- ambiguity handling (multiple samples/reports)

Tools must NOT assume successful execution.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- new soil sample registration
- tracking sample lifecycle
- generating soil health card
- interpreting nutrient values
- generating fertilizer recommendations
- handling delays or missing reports
- grievance escalation

---

## TOOL DESIGN REQUIREMENTS

- Naming format: shc_verb_noun (lowercase, underscores only)
- Each tool must represent ONE atomic API
- Tools should be independent (no chaining logic required)
