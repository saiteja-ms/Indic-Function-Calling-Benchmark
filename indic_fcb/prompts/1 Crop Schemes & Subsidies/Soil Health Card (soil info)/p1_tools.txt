THREE-AXIS EVALUATION DESIGN (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This benchmark evaluates LLMs on three independent
dimensions. The tool set MUST support test cases at
every meaningful cell of this 3-axis grid.

AXIS 1 — Conversation length:
  single-turn  : one user message
  multi-turn   : multiple user messages with state
                 evolving between them

AXIS 2 — Tool calls per turn:
  single-step  : exactly one tool call per turn
  multi-step   : multiple tool calls in the same turn
                 (parallel or parallel-multiple)

AXIS 3 — Task type:
  simple             : one clear tool, unambiguous
  parallel-multiple  : multiple tools called together,
                       no inter-call dependency
  irrelevance        : no tool can answer; model must
                       not call anything

To support all three axes, the tool set MUST include:

PUBLIC TOOLS (no session_token required) — at least 4:
  Enable single-turn, single-step, simple test cases.

PARALLEL-SAFE TOOL PAIRS — at least 4 pairs:
  Tools that read disjoint state and never mutate
  shared fields. Enable parallel-multiple cases.

CHAIN-CAPABLE TOOLS — at least 6:
  Tools whose parameter signatures or preconditions
  imply a required prior call. Enable multi-turn
  chain cases. The required prior call is inferred
  from the parameter signature, NOT from text in
  the description.

DOMAIN-BOUNDARY CLARITY:
  The tool set must NOT cover PM-KISAN income support,
  PMFBY crop insurance, PM-KUSUM solar pumps, fertilizer
  DBT subsidy, eNAM mandi trade, or weather forecasting
  — these belong to other UMANG services and enable
  irrelevance test cases.

FORBIDDEN — these will invalidate the benchmark:

  ✗ Saying "followed by Y" where Y is a tool name

ALLOWED — these are the ONLY ways to encode chain order:

  ✓ Abstract state preconditions

  ✓ Return value schemas
    ("returns sample_id and assigned lab_id")
  ✓ Description of what state the tool reads or
    mutates, expressed abstractly

The model being evaluated must INFER chain order from
parameter and return schemas — never read it from prose.

DOMAIN CONSTRAINTS (encode abstractly in descriptions)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are real Soil Health Card scheme rules — encode
them as preconditions in tool descriptions without
naming which other tools must satisfy them.

- A soil health card is valid for 3 years from
  issuance date.
- Sample collection follows a grid-based sampling
  pattern: one sample per 2.5 hectares for irrigated
  land; one per 10 hectares for rain-fed land.
- Samples are collected only during the recommended
  post-harvest window for the cropping season.
- Each sample is tested for 12 parameters: pH,
  electrical conductivity (EC), organic carbon (OC),
  nitrogen (N), phosphorus (P), potassium (K),
  sulphur (S), zinc (Zn), iron (Fe), copper (Cu),
  manganese (Mn), and boron (B).
- A lab must be MoA&FW-accredited and assigned by
  the state nodal officer.
- Test results must be uploaded to the SHC portal
  within 30 days of sample receipt.
- Card recommendations are crop-specific and use
  the farmer's primary cropping pattern.
- Re-test is allowed once per sample cycle if the
  farmer disputes results within 15 days.
- One farmer plot has only one active card per
  cycle.
- Land ownership must match revenue records for
  the plot to be eligible.
- A grievance is meaningful only after the card
  has been issued or sample has been collected.

Each tool description must contain (in order):

1. WHAT IT DOES — one sentence stating the action

2. STATE PRECONDITIONS — abstract conditions that
   must hold before this tool can succeed
   (e.g. "requires plot_registration_status: verified
    and sample_collection_status: not_requested")
   NEVER name other tools.

3. INPUT VALIDATION — what makes inputs invalid
   (e.g. "aadhaar_number must be exactly 12 digits;
    land_area_hectares must be > 0; crop must be in
    valid crop registry for the district")

4. RETURNS — key fields in the success response
   (e.g. "returns sample_id, scheduled collection
    date, and assigned field officer")

5. WHAT IT DOES NOT DO — at least one limitation
   (e.g. "does not perform the soil test;
    does not generate the card")

6. FAILURE CONDITIONS — at least one rejection scenario
   (e.g. "fails if the sampling window is closed,
    if no accredited lab is available for the
    district, or if a sample request is already
    active for this plot in the current cycle")
