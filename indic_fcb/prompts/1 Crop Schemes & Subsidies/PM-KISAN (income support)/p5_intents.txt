Every intent in this benchmark is positioned at
a specific cell of a 3-dimensional evaluation
grid. Each intent MUST declare its position on
all three axes:

AXIS 1 — Conversation length:
  single_turn  : one user message, one model
                 response
  multi_turn   : multiple user messages with
                 state evolving between them

AXIS 2 — Tool calls per turn:
  single_step  : exactly one tool call expected
                 in any single turn
  multi_step   : multiple tool calls expected
                 in the same turn (parallel or
                 parallel_multiple)

AXIS 3 — Task type:
  simple              : one clear tool, unambiguous
  parallel_multiple   : multiple tools called
                        together with no inter-call
                        dependency
  irrelevance         : no tool can answer; model
                        must not call anything

The combination of these three axes produces
the test cell.

WHAT IS AN INTENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

An intent is an abstract user goal, independent
of language and phrasing.

In this benchmark, an intent carries:
  - the THREE-AXIS POSITION
  - the STATE PRECONDITIONS that the archetype
    must be in for the intent to be coherent
  - the STATE TRANSITION the intent causes
    (what changes if the intent succeeds)
  - the COMPATIBLE ARCHETYPES that could
    plausibly hold this intent

When stubs are generated later, they will
implement exactly the state transitions defined
here, and they will validate against the
state preconditions defined here.

This means: intents are the source of truth.
Stubs follow intents.

Infer the state schema from the tools.jsonl
return values and parameter expectations.
Each enum field becomes a state field with
that enum's domain of values.

Common PM-KISAN state fields you should use
across intents (use exact names, lowercase):

  authenticated              : true | false
  session_token              : string | null
  registration_status        : not_registered |
                               applied | registered |
                               rejected
  ekyc_status                : not_started | pending |
                               completed | failed
  bank_seeding_status        : not_seeded | pending |
                               seeded | failed
  land_record_status         : not_validated |
                               validated | mismatch
  eligibility_status         : not_checked | eligible |
                               ineligible
  installments_credited      : integer 0-3
  installments_pending       : integer 0-3
  installments_rejected      : integer 0-3
  has_pending_over_90_days   : true | false
  has_active_grievance       : true | false
  grievance_status           : not_filed | filed |
                               under_review |
                               resolved | rejected
  payment_failure_reason     : null |
                               bank_account_invalid |
                               aadhaar_mismatch |
                               ekyc_pending |
                               land_record_dispute

You MAY add additional state fields if a tool's
return value or parameter implies one. Use the
exact field name as it appears in tools.jsonl
return schemas. State field names use
lowercase_with_underscores.

state_transition:
  MANDATORY on every intent
  format:
    {
      "reads": [list of state fields read],
      "writes": {state_field: new_value, ...}
    }
  reads: which state fields this intent's tools
    will read to compute response
  writes: which state fields will change if the
    intent succeeds
    Use {} for read-only intents.

  Examples:
    Simple status check:
      reads: ["registration_status",
              "installments_credited"]
      writes: {}

    eKYC completion:
      reads: ["ekyc_status",
              "authenticated"]
      writes: {
        "ekyc_status": "completed",
        "has_pending_over_90_days": false
      }

    Grievance filing:
      reads: ["registration_status"]
      writes: {
        "has_active_grievance": true,
        "grievance_status": "filed"
      }
