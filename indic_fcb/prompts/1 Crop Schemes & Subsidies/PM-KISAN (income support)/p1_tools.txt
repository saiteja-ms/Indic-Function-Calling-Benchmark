THREE-AXIS EVALUATION DESIGN (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This benchmark evaluates LLMs on three independent
dimensions. The tool set MUST support test cases at
every meaningful cell of this 3-axis grid.

AXIS 1 — Conversation length:
  single-turn  : one user message
  multi-turn   : multiple user messages with state
                 evolving between them

AXIS 2 — Tool calls per turn:
  single-step  : exactly one tool call per turn
  multi-step   : multiple tool calls in the same turn
                 (parallel or parallel-multiple)

AXIS 3 — Task type:
  simple             : one clear tool, unambiguous
  parallel-multiple  : multiple tools called together,
                       no inter-call dependency
  irrelevance        : no tool can answer; model must
                       not call anything

To support all three axes, the tool set MUST include:

PUBLIC TOOLS (no session_token required) — at least 4:
  Enable single-turn, single-step, simple test cases.

PARALLEL-SAFE TOOL PAIRS — at least 4 pairs:
  Tools that read disjoint state and never mutate
  shared fields. Enable parallel-multiple cases.

CHAIN-CAPABLE TOOLS — at least 6:
  Tools whose parameter signatures or preconditions
  imply a required prior call. Enable multi-turn
  chain cases. The required prior call is inferred
  from the parameter signature, NOT from text in
  the description.

DOMAIN-BOUNDARY CLARITY:
  The tool set must NOT cover crop insurance, mandi
  prices, fertilizer subsidy, KCC loans, soil health
  cards, or MGNREGA — these belong to other UMANG
  services and enable irrelevance test cases.

Each tool description must be SELF-CONTAINED.

FORBIDDEN — these will invalidate the benchmark:
  ✗ Naming other tools in the description
    ("call pmkisan_authenticate_farmer first")
  ✗ Saying "must be preceded by X" where X is a
    tool name
  ✗ Saying "followed by Y" where Y is a tool name
  ✗ Any cross-reference between tools by name

ALLOWED — these are the ONLY ways to encode chain order:
  ✓ Parameter signatures
    (a tool requiring session_token implicitly
     requires a prior authentication call)
  ✓ Abstract state preconditions
    ("requires beneficiary status: registered")
  ✓ Return value schemas
    ("returns session_token valid for 15 minutes")
  ✓ Description of what state the tool reads or
    mutates, expressed abstractly

The model being evaluated must INFER chain order from
parameter and return schemas — never read it from prose.

Example — CORRECT description:
  "Completes mandatory eKYC verification using Aadhaar OTP.
   Requires an active authentication session and a
   registered beneficiary with ekyc_status: pending.
   Returns the updated eKYC status. Fails if eKYC is
   already completed, if the beneficiary is not
   registered, or if the OTP is invalid. Does NOT
   handle Aadhaar enrolment or biometric updates."

Example — INCORRECT description:
  "Completes mandatory eKYC. Call pmkisan_authenticate_farmer
   first to get session_token. Then call
   pmkisan_track_installment_status to confirm release."

DOMAIN CONSTRAINTS (encode abstractly in descriptions)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are real PM-KISAN rules — encode them as
preconditions in tool descriptions without naming
which other tools must satisfy them.

- Authentication is required for write operations.
  Authentication produces a session_token.
- Eligibility requires valid Aadhaar, valid land
  ownership records, and not being excluded under
  scheme rules.
- eKYC must be completed before installments release.
- ₹6000/year is paid as 3 installments of ₹2000.
- Land ownership must be verified via state databases.
- Payment is transferred directly to the linked
  bank account.
- Installment is credited only if eligibility is
  confirmed, eKYC is completed, and bank details
  are valid.
- One Aadhaar maps to one beneficiary record only
  (duplicate prevention).
- Payments may fail due to incorrect bank details
  or name mismatch.
- A grievance is meaningful only if status has been
  verified first.

Each tool description must contain (in order):

1. WHAT IT DOES — one sentence stating the action

2. STATE PRECONDITIONS — abstract conditions that
   must hold before this tool can succeed
   (e.g. "requires beneficiary to be registered with
    ekyc_status: completed")
   NEVER name other tools.

3. INPUT VALIDATION — what makes inputs invalid
   (e.g. "Aadhaar must be exactly 12 digits;
    OTP must be 6 digits")

4. RETURNS — key fields in the success response
   (e.g. "returns ekyc_status and a list of
    affected installments")

5. WHAT IT DOES NOT DO — at least one limitation
   (e.g. "does not handle Aadhaar enrolment;
    does not reset OTPs")

6. FAILURE CONDITIONS — at least one rejection scenario
   (e.g. "fails if ekyc_status is already completed,
    if OTP is invalid, or if beneficiary is excluded")
