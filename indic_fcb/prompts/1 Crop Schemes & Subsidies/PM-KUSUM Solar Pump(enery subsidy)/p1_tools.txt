in the style of the Berkeley Function Calling Leaderboard
(BFCL) and tau-bench.

Your task: Generate tool schemas for the PM-KUSUM
(Pradhan Mantri Kisan Urja Suraksha evam Utthaan
Mahabhiyan - solar pump subsidy and grid-connected
solar) service on the UMANG app.

Generate AS MANY tools as needed for complete coverage.
Minimum 14, no upper limit. If a realistic farmer workflow

THREE-AXIS EVALUATION DESIGN (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This benchmark evaluates LLMs on three independent
dimensions. The tool set MUST support test cases at
every meaningful cell of this 3-axis grid.

AXIS 1 — Conversation length:
  single-turn  : one user message
  multi-turn   : multiple user messages with state
                 evolving between them

AXIS 2 — Tool calls per turn:
  single-step  : exactly one tool call per turn
  multi-step   : multiple tool calls in the same turn
                 (parallel or parallel-multiple)

AXIS 3 — Task type:
  simple             : one clear tool, unambiguous
  parallel-multiple  : multiple tools called together,
                       no inter-call dependency
  irrelevance        : no tool can answer; model must
                       not call anything

To support all three axes, the tool set MUST include:

PUBLIC TOOLS (no session_token required) — at least 4:
  Enable single-turn, single-step, simple test cases.

PARALLEL-SAFE TOOL PAIRS — at least 4 pairs:
  Tools that read disjoint state and never mutate
  shared fields. Enable parallel-multiple cases.

CHAIN-CAPABLE TOOLS — at least 6:
  Tools whose parameter signatures or preconditions
  imply a required prior call. Enable multi-turn
  chain cases. The required prior call is inferred
  from the parameter signature, NOT from text in
  the description.

DOMAIN-BOUNDARY CLARITY:
  The tool set must NOT cover PM-KISAN income support,
  PMFBY crop insurance, soil health cards, fertilizer
  subsidy, eNAM mandi trade, or general electricity
  bill payment — these belong to other UMANG services
  and enable irrelevance test cases.

Each tool description must be SELF-CONTAINED.

FORBIDDEN — these will invalidate the benchmark:
  ✗ Naming other tools in the description
  ✗ Saying "must be preceded by X" where X is a
    tool name
  ✗ Saying "followed by Y" where Y is a tool name
  ✗ Any cross-reference between tools by name

ALLOWED — these are the ONLY ways to encode chain order:
  ✓ Parameter signatures
    (a tool requiring session_token implicitly
     requires a prior authentication call)
  ✓ Abstract state preconditions
    ("requires application_status: approved and
     vendor_selection_status: confirmed")
  ✓ Return value schemas
    ("returns application_id and assigned
     vendor list for the district")
  ✓ Description of what state the tool reads or
    mutates, expressed abstractly

The model being evaluated must INFER chain order from
parameter and return schemas — never read it from prose.

Example — CORRECT description:
  "Confirms vendor selection for a sanctioned solar
   pump installation under PM-KUSUM Component B.
   Requires an authenticated session, an approved
   application, and a vendor_selection_status of
   pending. Returns the confirmed vendor_id,
   estimated installation_date, and farmer share
   amount due. Fails if the application is not
   approved, if the vendor is not empanelled for
   the district, or if the selection window has
   expired. Does NOT initiate payment or schedule
   the installation."

Example — INCORRECT description:
  "Confirms vendor selection. Call pmkusum_authenticate
   first to get session_token, then pmkusum_get_empanelled
   vendors to find a vendor, then call this tool."

DOMAIN CONSTRAINTS (encode abstractly in descriptions)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are real PM-KUSUM rules — encode them as
preconditions in tool descriptions without naming
which other tools must satisfy them.

- Component A is only for individual farmers, FPOs,
  cooperatives, or panchayats with at least 0.5 acres
  of barren or cultivable wasteland.
- Component B is only for off-grid farmers with no
  existing grid electricity connection for irrigation.
- Component C is only for farmers with an existing
  grid-connected electric pump.
- Pump capacity is capped at 7.5 HP for standard
  Component B applications.
- Central subsidy is 30% of benchmark cost.
- State subsidy is 30% (varies by state).
- Farmer share is 40% (varies based on category;
  reduced for SC/ST, North-East, and hilly states).
- Vendor must be empanelled by MNRE for the
  applicable district and pump capacity range.
- Subsidy is disbursed only after successful
  installation and verification.
- Land ownership must be verified via state revenue
  records before application can proceed.
- One farmer may apply for only ONE Component B
  pump per landholding.
- A grievance is meaningful only after application
  status has been retrieved.
