You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
PM-KUSUM (Pradhan Mantri Kisan Urja Suraksha evam Utthaan Mahabhiyan)
solar pump subsidy service on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Eligibility checking for solar pump subsidy
- Application submission for solar pump installation
- Subsidy calculation and beneficiary contribution
- Vendor selection and approval
- Installation scheduling and tracking
- Physical inspection and verification
- Subsidy disbursement tracking
- Grid connection (if applicable)
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Eligibility dependency:
  Farmer must satisfy:
    - land ownership or valid lease
    - access to irrigation land
    - non-duplication (cannot receive multiple subsidies for same asset)

- Application requirement:
  Subsidy can only be applied after eligibility check.

- Subsidy structure:
  Subsidy is shared between:
    - central government
    - state government
    - farmer contribution

- Vendor dependency:
  Installation must be carried out by empanelled vendors.

- Installation requirement:
  Subsidy is released ONLY after successful installation.

- Inspection dependency:
  Physical verification must confirm installation before payment.

- Grid/off-grid distinction:
  Some pumps may be grid-connected, others standalone.

- State-specific variation:
  Subsidy percentage and rules may vary across states.

- Grievances should ONLY be raised after checking application or subsidy status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- application_status:
  not_applied → submitted → under_review → approved → rejected

- installation_status:
  not_started → scheduled → in_progress → completed → verified

- subsidy_status:
  not_initiated → pending → disbursed → failed

- vendor_status:
  not_selected → selected → assigned

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- farmer not eligible but attempts application
- duplicate subsidy request
- invalid or missing land details
- vendor not available in region
- installation delay or failure
- inspection failure (installation incomplete or incorrect)
- subsidy calculation mismatch
- partial installation
- grid connection failure
- subsidy payment delay or failure

Descriptions must explicitly reflect these cases.

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (eligibility, land ownership, duplication)

- failure scenarios (installation failure, subsidy delay)

Tools must NOT assume success-only execution.
