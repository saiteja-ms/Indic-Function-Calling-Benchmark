THREE-AXIS EVALUATION — STRUCTURAL DEFINITIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

AXIS 1 — conversation_length:
  single_turn = exactly one user message in
                the conversation
  multi_turn  = two or more user messages

AXIS 2 — tool_calls_per_turn:
  single_step = every ground_truth turn has
                at most ONE tool_call
  multi_step  = at least one ground_truth turn
                has TWO or more tool_calls

AXIS 3 — task_type:
  simple              = at most one tool call
                        per turn AND no
                        irrelevance pattern
  parallel_multiple   = multiple tool calls in
                        one turn AND those calls
                        target DIFFERENT tools
  irrelevance         = ALL ground_truth turns
                        have null_call: true AND
                        at least one has an
                        irrelevance_reason

NOTE: parallel (same tool, different params,
multiple calls in one turn) maps to task_type
"simple" — the multi-step nature is captured
by AXIS 2, not AXIS 3. parallel_multiple is
reserved for DIFFERENT tools called together.

An intent carries:
  - three-axis position
  - state_preconditions
  - state_transition (reads + writes)
  - compatible_archetypes

State preconditions + transitions are the
SPECIFICATION for stub_logic.py to implement.

CATEGORY-SPECIFIC COVERAGE RULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

── SIMPLE ──────────────────────────────────────────

One intent per tool minimum. Additional intents
for tools with meaningful parameter variations
(e.g. calculate_premium varies by crop type
and land area).

── MULTIPLE ────────────────────────────────────────

Distractor traps — each appears twice with
different user phrasings.

A distractor trap is two tools that would
plausibly seem to solve the SAME user request
but only ONE is correct.

  TRAP A: "what's my insurance status"
    Correct  : pmfby_get_enrollment_status
    Distractor: pmfby_get_policy_details
    Trap: enrollment status is the lifecycle
    state; policy details is the document.

  TRAP B: "how much will I pay for insurance"
    Correct  : pmfby_calculate_premium
    Distractor: pmfby_get_premium_receipt
    Trap: receipt is for paid premium; user
    wants pre-enrollment calculation.

  TRAP C: "I want to insure my paddy crop"
    Correct  : pmfby_submit_enrollment
    Distractor: pmfby_check_eligibility
    Trap: eligibility is informational; user
    wants the action of enrolling.

  TRAP D: "can I get insurance for cotton in
          my district"
    Correct  : pmfby_get_notified_crops
    Distractor: pmfby_check_eligibility
    Trap: notified crops is a list lookup;
    eligibility is per-farmer.

  TRAP E: "show me my insurance policy"
    Correct  : pmfby_get_policy_details
    Distractor: pmfby_get_premium_receipt
    Trap: policy details show coverage;
    receipt only shows payment.

  TRAP F: "I want to complain about delayed
          premium refund"
    Correct  : pmfby_raise_grievance
    Distractor: pmfby_get_premium_receipt
    Trap: receipt does not address the
    grievance even if it shows the data.

  TRAP G: "check if I can apply for insurance"
    Correct  : pmfby_check_eligibility
    Distractor: pmfby_get_notified_crops
    Trap: same pair as D inverted — user
    wants eligibility, not crop list.

── PARALLEL ────────────────────────────────────────

Same-tool simultaneous calls. The intent has
multiple calls to ONE tool in a single turn:
  - get_enrollment_status for two crops
  - calculate_premium for two crop types
  - get_cutoff_dates for two seasons
  - track_grievance_status for two IDs
  - get_notified_crops for two districts

── PARALLEL_MULTIPLE ───────────────────────────────

Different-tool simultaneous calls. The intent
has calls to MULTIPLE DIFFERENT tools in a
single turn, with no dependency between them:
  - get_enrollment_status + get_premium_receipt
  - get_notified_crops + get_cutoff_dates
  - get_policy_details + get_premium_receipt
  - get_notified_crops + get_insurer_contact
  - get_cutoff_dates + get_insurer_contact

STRICT: never pair tools where one depends on
the other's output.

── TASK_IRRELEVANCE ────────────────────────────────

Topics where no PMFBY enrollment tool applies:
  - PM-KISAN income support installments
  - soil health card status or test results
  - MSP procurement token booking
  - mandi prices (eNAM)
  - fertilizer subsidy DBT amount
  - SDRF/NDRF disaster relief claim
  - PMFBY loss claim (separate claim usecase)
  - KCC loan status
  - PM-KUSUM solar pump
  - weather forecast for sowing
  - cattle or livestock insurance

── BASE ────────────────────────────────────────────

Multi-turn chains. chain_order_enforced: true.

  CHAIN A — New enrollment flow
    domain_constraint: "premium can only be
    calculated after eligibility is confirmed,
    and enrollment can only be submitted after
    land records are validated"
    Order: authenticate → check_eligibility →
           validate_land_records →
           calculate_premium → submit_enrollment →
           pay_premium

  CHAIN B — Premium payment retry
    domain_constraint: "premium can be paid
    only after an enrollment record exists"
    Order: authenticate → get_enrollment_status →
           pay_premium → get_premium_receipt

  CHAIN C — Policy verification
    domain_constraint: "policy details are
    available only after enrollment is confirmed"
    Order: authenticate → get_enrollment_status →
           get_policy_details

  CHAIN D — Crop declaration update
    domain_constraint: "declaration update
    requires active enrollment before cutoff"
    Order: authenticate → get_enrollment_status →
           update_crop_declaration

  CHAIN E — Grievance flow
    domain_constraint: "grievance requires an
    enrollment to file against"
    Order: authenticate → get_enrollment_status →
           raise_grievance

── MISS_PARAM ──────────────────────────────────────

Parameters commonly omitted:
  - aadhaar_number missing from eligibility check
  - crop_name missing from premium calculation
  - season missing from cutoff date lookup
  - land_area_hectares missing from premium calc
  - survey_number missing from land validation
  - otp missing from authentication
  - district missing from notified crops lookup
  - insurer_id missing from policy details

── MISS_FUNC ───────────────────────────────────────

Actions PMFBY genuinely cannot perform — no
tool exists for these:

  - enroll after the season cutoff date has
    passed (system blocks; no late-enrollment
    function)
  - change insured crop after policy is issued
    (no mid-policy modification)
  - request premium refund for an active policy
    (no refund function for active policy)
  - transfer policy to another farmer (no
    transfer mechanism)
  - reduce sum insured after enrollment (sum
    insured is fixed by scale of finance)
  - enroll a tenant farmer without owner consent
    (PMFBY requires land ownership)
  - file a loss claim through this enrollment
    portal (claim is a separate service)
  - enroll for a non-notified crop in the
    district (system cannot accept)

── LONG_CONTEXT ────────────────────────────────────

One long_context intent per base chain (5 total).
Each has 3-5 padding user turns BEFORE the chain
begins. Padding turns have tool_calls: [] and
null_call: true.

COMPATIBLE ARCHETYPE GUIDANCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Compatibility uses ONLY archetype attributes
from persona.json. NEVER use state fields as
filters. Always reference archetypes by their
canonical ID (ARC_01 to ARC_16). Do NOT invent
descriptive IDs.

MORE COMPATIBLE for PMFBY enrollment:
  - landholding_category: small, medium, large
  - farmer_category: owner (PMFBY requires
    land ownership in most states)
  - region: hindi_belt, east_bengal_odisha,
    maharashtra_gujarat (flood/drought-prone,
    high PMFBY uptake)
  - scheme_experience: repeat_beneficiary or
    has_filed_grievance_before
  - irrigation_type: rain_fed (highest insurance
    need due to weather risk)

LESS COMPATIBLE:
  - farmer_category: tenant or sharecropper
    (cannot enroll directly in most states)

FORCED COMPATIBLE:
  - tenant/sharecropper archetypes MUST appear
    in miss_func intents (system blocks them)
  - digital_literacy level_1 archetypes MUST
    appear in simple and multiple intents
    (low-literacy use cases via CSC)

PROCESS for picking compatible archetypes:
  1. Open persona.json
  2. For each of ARC_01 through ARC_16, check:
     - landholding_category
     - farmer_category
     - region
     - irrigation_type
     - digital_literacy
     - scheme_experience
  3. Apply rules above to decide compatibility
  4. List archetype_id values (ARC_XX format)

Every archetype must appear in at least 3 intents
across all categories.
