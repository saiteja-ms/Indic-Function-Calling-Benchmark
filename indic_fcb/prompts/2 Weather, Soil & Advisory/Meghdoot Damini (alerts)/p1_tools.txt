You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
Meghdoot (agro-advisory alerts) and Damini (lightning alerts)
service on the UMANG app.

The number of tools should be sufficient (typically 10–14 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Retrieving real-time lightning alerts (Damini)
- Fetching weather-based agro advisories (Meghdoot)
- Location-based alert queries
- Severe weather warnings (rain, storm, heatwave)
- Safety advisory recommendations
- Alert subscription and notification preferences
- Alert history retrieval
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Public vs authenticated access:
  - Basic alerts (lightning proximity, weather alerts) are PUBLIC
  - Subscription, preferences, and history REQUIRE authentication

- Location specificity:
  Alerts are generated based on precise location (village/district/GPS).
  Alerts without location are INVALID.

- Real-time lightning alerts (Damini):
  - Based on satellite/sensor data
  - Valid only within a short time window (~minutes)
  - Alerts expire quickly

- Agro-advisory alerts (Meghdoot):
  - Based on crop + weather + location
  - Generated periodically (not real-time like lightning)

- Alert validity:
  Old alerts MUST NOT be treated as active alerts.

- Subscription requirement:
  Farmers must subscribe to receive notifications.

- Safety-critical nature:
  Lightning alerts MUST include safety recommendations.

- Grievances should ONLY be raised after verifying alert availability/status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- alert_status:
  generated → active → expired

- subscription_status:
  not_subscribed → subscribed → unsubscribed

- alert_query_state:
  invalid_location → valid_query → alert_available / alert_not_available

Tools must define:
- when alerts are valid
- when alerts are expired or unavailable

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- invalid or missing location
- no alerts available for region
- expired alerts being queried
- conflicting alert types (multiple alerts simultaneously)
- delayed or missing alert updates
- subscription not active but user expecting alerts
- incorrect location mapping
- duplicate alert notifications
- stale advisory data

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (location required, valid alert type)
- failure conditions (no alerts, expired alerts)
- ambiguity handling (multiple alerts)

Tools must NOT assume alerts always exist.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- farmer checking real-time lightning alert
- receiving agro-advisory for crops
- reacting to severe weather alerts
- subscribing/unsubscribing to alerts
- handling no-alert scenarios
- grievance escalation for missed alerts

---

## TOOL DESIGN REQUIREMENTS

- Naming format:
  - damini_verb_noun for lightning tools
  - meghdoot_verb_noun for advisory tools
- Lowercase, underscores only
- Each tool must represent ONE atomic API
- Tools should be independent (no chaining logic required)
