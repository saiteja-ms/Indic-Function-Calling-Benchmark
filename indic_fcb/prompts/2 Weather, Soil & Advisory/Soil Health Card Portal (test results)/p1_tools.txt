You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
Soil Health Card Portal (soil test results and report retrieval)
service on the UMANG app.

The number of tools should be sufficient (typically 10–14 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Searching Soil Health Card reports
- Retrieving and downloading soil test reports
- Viewing nutrient analysis (N, P, K, pH, etc.)
- Tracking soil sample processing status
- Accessing historical reports
- Filtering reports by land parcel
- Viewing lab/testing center details
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED for accessing personal soil data:
  Aadhaar + OTP verification must be completed first.
  Authentication returns a session_token.

- Land-parcel dependency:
  Each Soil Health Card report is tied to a specific land parcel.

- Lab dependency:
  Reports are available ONLY after lab testing is complete.

- Periodicity:
  Soil Health Cards are typically generated once every 2 years.

- Data immutability:
  Nutrient values (N, P, K, pH, etc.) are lab-measured and cannot be modified.

- Recommendation dependency:
  Fertilizer recommendations depend strictly on soil test reports.

- Multiple reports:
  A farmer can have multiple reports across years and land parcels.

- Grievances should ONLY be raised after checking report or sample status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- sample_status:
  registered → collected → in_transit → under_testing → report_ready

- report_status:
  not_available → available → downloaded

- query_state:
  invalid_query → valid_query → filtered → result_found / result_empty

Tools must define:
- when data is accessible
- when access is invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- no report exists for given Aadhaar
- invalid or missing land_parcel_id
- report requested before testing completion
- partial reports (some nutrients missing)
- multiple reports for same land parcel (ambiguity)
- outdated reports being requested
- lab delay or stalled testing
- incorrect mapping of land parcel to farmer
- download failure

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (Aadhaar format, land parcel linkage)
- failure conditions (report not ready, invalid query)
- ambiguity handling (multiple reports)

Tools must NOT assume successful retrieval.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- farmer checking latest report
- accessing historical reports
- checking sample status before report availability
- retrieving nutrient values
- handling missing or delayed reports
- grievance escalation

---

## TOOL DESIGN REQUIREMENTS

- Naming format: shcportal_verb_noun (lowercase, underscores only)
- Each tool must represent ONE atomic API
- Tools should be independent (no chaining logic required)
