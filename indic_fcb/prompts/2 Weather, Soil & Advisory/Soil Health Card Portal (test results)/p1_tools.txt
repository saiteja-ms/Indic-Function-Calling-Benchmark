You are building a function-calling benchmark dataset
in the style of the Berkeley Function Calling Leaderboard
(BFCL) and tau-bench.

Your task: Generate tool schemas for the Soil Health
Card (SHC) Portal — the farmer-facing access layer for
retrieving completed test results, nutrient reports,
fertilizer recommendations, and historical comparisons.

This is DISTINCT from the SHC scheme enrollment covered
separately. This usecase covers only the READ and ADVISORY
layer: farmers who already have an issued card accessing
its contents, comparing across cycles, and acting on
recommendations.

Generate AS MANY tools as needed for complete coverage.
Minimum 14, no upper limit. If a realistic farmer workflow
needs an additional tool not listed below, add it.

THREE-AXIS EVALUATION DESIGN (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This benchmark evaluates LLMs on three independent
dimensions. The tool set MUST support test cases at
every meaningful cell of this 3-axis grid.

AXIS 1 — Conversation length:
  single-turn  : one user message
  multi-turn   : multiple user messages with state
                 evolving between them

AXIS 2 — Tool calls per turn:
  single-step  : exactly one tool call per turn
  multi-step   : multiple tool calls in the same turn
                 (parallel or parallel-multiple)

AXIS 3 — Task type:
  simple             : one clear tool, unambiguous
  parallel-multiple  : multiple tools called together,
                       no inter-call dependency
  irrelevance        : no tool can answer; model must
                       not call anything

To support all three axes, the tool set MUST include:

PUBLIC TOOLS (no session_token required) — at least 5:
  The portal is primarily a read-only advisory layer.
  Most lookups are public. Enable single-turn,
  single-step, simple test cases.

PARALLEL-SAFE TOOL PAIRS — at least 4 pairs:
  Tools that read disjoint data and never mutate
  shared state. Enable parallel-multiple cases.

CHAIN-CAPABLE TOOLS — at least 4:
  Tools whose parameter signatures or preconditions
  imply a required prior call. Enable multi-turn
  chain cases. The required prior call is inferred
  from the parameter signature, NOT from text in
  the description.

DOMAIN-BOUNDARY CLARITY:
  The tool set must NOT cover soil sample collection
  scheduling, lab assignment, or scheme enrollment
  (covered in the SHC scheme usecase). Must NOT cover
  PM-KISAN, PMFBY, PM-KUSUM, weather forecasting,
  or eNAM mandi trade — these belong to other
  UMANG services and enable irrelevance test cases.

FORBIDDEN — these will invalidate the benchmark:
  ✗ Naming other tools in the description
  ✗ Saying "must be preceded by X" where X is a
    tool name
  ✗ Saying "followed by Y" where Y is a tool name
  ✗ Any cross-reference between tools by name

ALLOWED — these are the ONLY ways to encode chain order:
  ✓ Parameter signatures
    (a tool requiring session_token implicitly
     requires a prior authentication call)
  ✓ Abstract state preconditions
    ("requires card_status: issued and
     test_status: completed")
  ✓ Return value schemas
    ("returns card_id and nutrient_levels object
     with 12 parameter readings")
  ✓ Description of what state the tool reads or
    mutates, expressed abstractly

The model being evaluated must INFER chain order from
parameter and return schemas — never read it from prose.

DOMAIN CONSTRAINTS (encode abstractly in descriptions)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are real SHC portal rules — encode them as
preconditions in tool descriptions without naming
which other tools must satisfy them.

- A card is valid for 3 years from issuance date;
  expired cards are viewable but recommendations
  are marked outdated.
- Recommendations are crop-specific; a farmer must
  specify the crop to get relevant dosage advice.
- Nutrient levels are rated on a 4-point scale:
  low, medium, sufficient, high.
- Stage-wise schedules divide crop growth into
  pre-sowing, basal, top-dressing, and foliar stages.
- Historical comparisons require at least 2 issued
  cards for the same plot.
- A farmer can access only cards linked to their
  Aadhaar-verified plot ownership.
- PDF download requires an authenticated session.
- Sharing a card with an extension officer requires
  the officer's registered ID in the KVK network.
- A grievance about incorrect results requires the
  specific card_id and parameter_name in dispute.
- Organic amendment recommendations are separate from
  chemical fertilizer recommendations and cover
  compost, vermicompost, green manure, and biofertilizer.

Each tool description must contain (in order):

1. WHAT IT DOES — one sentence stating the action

2. STATE PRECONDITIONS — abstract conditions that
   must hold before this tool can succeed
   (e.g. "requires card_status: issued and
    test_status: completed")
   NEVER name other tools.

3. INPUT VALIDATION — what makes inputs invalid
   (e.g. "card_id must exist in the portal;
    soil_parameter must be one of the 12 supported
    enum values; aadhaar_number must be 12 digits")

4. RETURNS — key fields in the success response
   (e.g. "returns parameter_name, measured_value,
    unit, nutrient_rating, and district_average
    for comparison")

5. WHAT IT DOES NOT DO — at least one limitation
   (e.g. "does not schedule a new soil test;
    does not order fertilizer")

6. FAILURE CONDITIONS — at least one rejection scenario
   (e.g. "fails if the card_status is not_issued,
    if the card belongs to a different farmer,
    or if the requested soil_parameter is not
    among the 12 tested parameters")
