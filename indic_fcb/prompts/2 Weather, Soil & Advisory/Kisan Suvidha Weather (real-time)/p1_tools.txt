You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
Kisan Suvidha Weather (real-time weather information)
service on the UMANG app.

The number of tools should be sufficient (typically 10–14 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Fetching current weather conditions
- Retrieving hourly and daily forecasts
- Querying weather by location (village/district)
- Accessing extreme weather alerts
- Viewing historical weather summaries
- Generating weather-based advisories
- Managing alert subscriptions
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Public vs authenticated access:
  - Weather data (current + forecast) is PUBLIC
  - Subscriptions, preferences, and grievances REQUIRE authentication

- Location specificity:
  Weather queries must include a valid location (village/district/GPS).
  Generic queries without location are INVALID.

- Forecast limits:
  Forecasts are reliable only up to ~7–10 days.

- Real-time vs forecast distinction:
  - Current weather reflects near real-time data
  - Forecast is predictive and may change

- Historical data limitation:
  Only recent past data (e.g., last 7–30 days) is available.

- Data variability:
  Weather data may differ across sources and updates.

- Advisory nature:
  Weather tools provide information ONLY — no direct farm actions.

- Grievances should ONLY be raised after verifying weather data.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- query_state:
  invalid_location → valid_query → data_available / data_not_available

- data_freshness:
  real_time → recent → stale

- forecast_state:
  generated → updated → expired

- subscription_status:
  not_subscribed → subscribed → unsubscribed

Tools must define:
- when data is valid
- when data is stale or unavailable

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- missing or invalid location
- no weather data available for region
- stale or outdated data
- conflicting forecast results
- incorrect or partial data
- extreme weather not reflected in forecast
- ambiguous location names
- duplicate or delayed updates
- user expecting alerts without subscription

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (location required, valid query inputs)
- failure conditions (no data, invalid query)
- ambiguity handling (multiple matching locations)

Tools must NOT assume successful data retrieval.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- farmer checking current weather
- planning using forecasts
- checking rainfall before irrigation
- handling missing or delayed data
- subscribing to weather alerts
- grievance escalation

---

## TOOL DESIGN REQUIREMENTS

- Naming format: ksweather_verb_noun (lowercase, underscores only)
- Each tool must represent ONE atomic API
- Tools should be independent (no chaining logic required)
