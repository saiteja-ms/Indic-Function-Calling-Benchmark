You are building a function-calling benchmark dataset
in the style of the Berkeley Function Calling Leaderboard
(BFCL) and tau-bench.

Your task: Generate tool schemas for the Crop Advisory
and ATMA (Agricultural Technology Management Agency)
service on the UMANG app.

ATMA is the district-level agricultural extension
delivery system. It connects farmers to Krishi Vigyan
Kendras (KVKs), subject matter specialists, farm
schools, demonstrations, and training programmes.
This usecase covers expert advisory access, training
registration, demonstration plot visits, and
personalised crop management guidance.

Generate AS MANY tools as needed for complete coverage.
Minimum 14, no upper limit. If a realistic farmer
workflow needs an additional tool not listed below,
add it.

THREE-AXIS EVALUATION DESIGN (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This benchmark evaluates LLMs on three independent
dimensions. The tool set MUST support test cases at
every meaningful cell of this 3-axis grid.

AXIS 1 — Conversation length:
  single-turn  : one user message
  multi-turn   : multiple user messages with state
                 evolving between them

AXIS 2 — Tool calls per turn:
  single-step  : exactly one tool call per turn
  multi-step   : multiple tool calls in the same turn
                 (parallel or parallel-multiple)

AXIS 3 — Task type:
  simple             : one clear tool, unambiguous
  parallel-multiple  : multiple tools called together,
                       no inter-call dependency
  irrelevance        : no tool can answer; model must
                       not call anything

To support all three axes, the tool set MUST include:

PUBLIC TOOLS (no session_token required) — at least 5:
  ATMA advisory lookups are mostly public information
  services. Enable single-turn, single-step, simple
  test cases.

PARALLEL-SAFE TOOL PAIRS — at least 4 pairs:
  Tools that read disjoint data and never mutate
  shared state. Enable parallel-multiple cases.

CHAIN-CAPABLE TOOLS — at least 5:
  Tools whose parameter signatures or preconditions
  imply a required prior call. Enable multi-turn
  chain cases. The required prior call is inferred
  from the parameter signature, NOT from text in
  the description.

DOMAIN-BOUNDARY CLARITY:
  The tool set must NOT cover weather forecasting
  (Kisan Suvidha / Meghdoot), soil test scheduling
  (SHC scheme), market prices (eNAM / Kisan Suvidha),
  PM-KISAN income support, PMFBY crop insurance, or
  PM-KUSUM solar pumps — these belong to other UMANG
  services and enable irrelevance test cases.

DOMAIN CONSTRAINTS (encode abstractly in descriptions)

These are real ATMA rules — encode them as
preconditions in tool descriptions without naming
which other tools must satisfy them.

- ATMA operates at the district level; advisories
  and programmes are district-and-crop specific.
- A farmer must be registered in the ATMA farmer
  database (linked to Aadhaar) to register for
  training or submit queries.
- Training programmes have a maximum participant
  limit; registration closes when capacity is full.
- Training certificates are issued only after
  attendance is confirmed by the KVK officer.
- Farm school visits require prior scheduling and
  are limited to registered ATMA farmers.
- Expert queries are routed to the Subject Matter
  Specialist for the relevant crop; response SLA
  is 3 working days.
- Technology packages are agro-climatic zone
  specific and cover variety selection, spacing,
  input schedule, and harvesting guidance.
- IPM advisories are season and pest-pressure
  specific; they are updated weekly during
  active crop seasons.
- A grievance about an unresponsive officer
  requires the officer_id and the query_id that
  went unanswered.
- Advisory bulletins are published by ICAR and
  state agriculture departments; they are read-only.

Each tool description must contain (in order):

1. WHAT IT DOES — one sentence stating the action

2. STATE PRECONDITIONS — abstract conditions that
   must hold before this tool can succeed
   (e.g. "requires farmer_profile_status: registered
    and training_registration_status: attended")
   NEVER name other tools.

3. INPUT VALIDATION — what makes inputs invalid
   (e.g. "district must be in the ATMA coverage
    network; aadhaar_number must be exactly 12 digits;
    crop must be in the district's notified advisory
    crop list")

4. RETURNS — key fields in the success response
   (e.g. "returns query_id, assigned_specialist_name,
    expected_response_date, and query_status")

5. WHAT IT DOES NOT DO — at least one limitation
   (e.g. "does not guarantee expert response within
    SLA; does not handle purchase of inputs or
    seeds recommended in the advisory")

6. FAILURE CONDITIONS — at least one rejection scenario
   (e.g. "fails if farmer_profile_status is
    not_registered, if the training programme is
    full or cancelled, or if the farmer is already
    registered for the same programme")
