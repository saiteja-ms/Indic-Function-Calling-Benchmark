You are building a function-calling benchmark dataset
in the style of the Berkeley Function Calling Leaderboard
(BFCL) and tau-bench.

Your task: Generate tool schemas for the Kisan Call
Centre (KCC) service on the UMANG app.

KCC is the national farmer helpline (toll-free
1800-180-1551) operated by the Ministry of Agriculture
and Farmers Welfare. It provides farmers with real-time
advisory responses from agricultural experts, grievance
registration against government schemes and officials,
query tracking, escalation management, and feedback
collection. On UMANG, farmers can submit queries,
track responses, raise grievances, and access the
query history without calling the phone line.

This usecase covers ONLY the KCC digital interface —
query submission, tracking, escalation, and feedback.
It does NOT cover the actual advisory content (that
is covered in ATMA/Kisan Suvidha), scheme transactions
(covered in PM-KISAN, PMFBY etc.), or market prices
(covered in eNAM/Kisan Suvidha).

Generate AS MANY tools as needed for complete coverage.
Minimum 14, no upper limit. If a realistic farmer
workflow needs an additional tool not listed below,
add it.

THREE-AXIS EVALUATION DESIGN (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This benchmark evaluates LLMs on three independent
dimensions. The tool set MUST support test cases at
every meaningful cell of this 3-axis grid.

AXIS 1 — Conversation length:
  single-turn  : one user message
  multi-turn   : multiple user messages with state
                 evolving between them

AXIS 2 — Tool calls per turn:
  single-step  : exactly one tool call per turn
  multi-step   : multiple tool calls in the same turn
                 (parallel or parallel-multiple)

AXIS 3 — Task type:
  simple             : one clear tool, unambiguous
  parallel-multiple  : multiple tools called together,
                       no inter-call dependency
  irrelevance        : no tool can answer; model must
                       not call anything

To support all three axes, the tool set MUST include:

PUBLIC TOOLS (no session_token required) — at least 4:
  KCC category lookup, expert availability, and
  service scope information are public. Enable
  single-turn, single-step, simple test cases.

PARALLEL-SAFE TOOL PAIRS — at least 4 pairs:
  Tools that read disjoint state and never mutate
  shared fields. Enable parallel-multiple cases.
  Natural pairs:
  - get_query_status + get_grievance_status
  - get_query_response + get_expert_availability
  - get_kcc_categories + get_escalation_status
  - get_query_history + get_grievance_history

CHAIN-CAPABLE TOOLS — at least 5:
  Tools whose parameter signatures or preconditions
  imply a required prior call. Enable multi-turn
  chain cases. The required prior call is inferred
  from the parameter signature, NOT from text in
  the description.

DOMAIN-BOUNDARY CLARITY:
  The tool set must NOT cover actual agricultural
  advisory content (ATMA), scheme enrollment or
  payments (PM-KISAN, PMFBY), market prices (eNAM,
  Kisan Suvidha), soil testing (SHC), weather
  forecasting (Meghdoot), or disaster relief (SDRF)
  — these belong to other UMANG services and enable
  irrelevance test cases. KCC handles the INTERFACE
  and ROUTING layer, not the content.

FORBIDDEN — these will invalidate the benchmark:
  ✗ Naming other tools in the description
  ✗ Saying "must be preceded by X" where X is a
    tool name
  ✗ Saying "followed by Y" where Y is a tool name
  ✗ Any cross-reference between tools by name

ALLOWED — these are the ONLY ways to encode chain order:
  ✓ Parameter signatures
    (a tool requiring session_token implicitly
     requires a prior authentication call)
  ✓ Abstract state preconditions
    ("requires query_status: responded and
     response_satisfaction: unsatisfied")
  ✓ Return value schemas
    ("returns query_id, assigned expert category,
     and expected response SLA")
  ✓ Description of what state the tool reads or
    mutates, expressed abstractly

The model being evaluated must INFER chain order from
parameter and return schemas — never read it from prose.

DOMAIN CONSTRAINTS (encode abstractly in descriptions)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are real KCC operational rules — encode them
as preconditions in tool descriptions without naming
which other tools must satisfy them.

- KCC operates in 22 scheduled languages; query
  submission requires specifying preferred language.
- Query response SLA is 72 hours for standard
  queries; 24 hours for urgent crop protection
  queries during active pest outbreaks.
- Escalation is allowed when SLA is exceeded or
  when the farmer rates the response as unsatisfied.
- A farmer may submit at most 3 open queries
  simultaneously; new queries are rejected until
  an existing one is closed.
- Scheme grievances are routed to the relevant
  scheme's nodal officer; the routing is automatic
  based on grievance category.
- Anonymous queries are accepted for sensitive
  topics but cannot be escalated or tracked
  without a query_id.
- A grievance about an official requires the
  official's designation and district.
- Response feedback must be submitted within 7
  days of the response; after that the query
  is auto-closed.
- Query history is retained for 2 years.
- A closed query cannot be reopened; a new query
  must be submitted.

Each tool description must contain (in order):

1. WHAT IT DOES — one sentence stating the action

2. STATE PRECONDITIONS — abstract conditions that
   must hold before this tool can succeed
   (e.g. "requires query_status: responded and
    response_feedback_status: not_submitted")
   NEVER name other tools.

3. INPUT VALIDATION — what makes inputs invalid
   (e.g. "mobile_number must be exactly 10 digits;
    query_category must be one of the supported
    enum values; query_text cannot be empty")

4. RETURNS — key fields in the success response
   (e.g. "returns query_id, assigned_expert_category,
    expected_response_date, and query_status")

5. WHAT IT DOES NOT DO — at least one limitation
   (e.g. "does not provide the advisory content
    directly; does not route to scheme-specific
    portals; does not guarantee a specific expert
    response")

6. FAILURE CONDITIONS — at least one rejection scenario
   (e.g. "fails if the farmer already has 3 open
    queries, if the query_category is not supported,
    or if the query_text is empty")
