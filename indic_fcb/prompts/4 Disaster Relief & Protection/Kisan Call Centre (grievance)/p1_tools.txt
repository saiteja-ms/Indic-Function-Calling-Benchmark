You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
Kisan Call Centre (farmer grievance and support system)
service on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Raising grievances across multiple services
- Categorizing and routing issues
- Assigning support agents or experts
- Tracking grievance status
- Providing responses and resolutions
- Escalating unresolved issues
- Closing grievances
- Feedback submission

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Multi-domain support:
  Grievances can relate to:
    - PM-KISAN
    - PMFBY
    - PM-KUSUM
    - Weather/Advisory
    - Market/Trade
    - Soil Health

- Categorization dependency:
  Grievance must be categorized correctly before routing.

- Ticket-based system:
  Each grievance generates a unique ticket_id.

- Assignment dependency:
  Grievance must be assigned to an appropriate expert/department.

- Response dependency:
  Resolution depends on investigation or system validation.

- Escalation logic:
  Unresolved grievances can be escalated to higher authorities.

- Closure requirement:
  Grievance can only be closed after resolution or user confirmation.

- Feedback loop:
  Farmers can provide feedback after resolution.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- grievance_status:
  raised → assigned → in_progress → resolved → closed → escalated

- assignment_status:
  not_assigned → assigned → reassigned

- response_status:
  not_provided → provided → acknowledged

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- invalid or unclear grievance description
- incorrect categorization
- duplicate grievance submission
- grievance raised without checking prior status
- unassigned or delayed assignment
- no response from expert
- incorrect resolution
- repeated escalation
- grievance closed prematurely
- conflicting information across systems

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (category, description required)
- rejection conditions (duplicate or invalid grievance)
- failure scenarios (no assignment, delayed response)

Tools must NOT assume successful resolution.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- farmer raising grievance
- tracking grievance status
- receiving responses
- escalation of unresolved issues
- closing grievance
- feedback submission
- handling incorrect or unresolved cases

---

## TOOL DESIGN REQUIREMENTS

- Naming format: kcc_verb_noun (lowercase, underscores only)
- Each tool must represent ONE atomic API
- Tools should be independent (no chaining logic required)
