You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
Cold Storage / Horticulture Cluster Infrastructure service
on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- User authentication
- Applying for cold storage / cluster infrastructure support
- Checking eligibility (individual vs group/FPO)
- Submitting project proposals
- Infrastructure approval and tracking
- Facility discovery (existing cold storages)
- Capacity availability lookup
- Booking storage space
- Usage tracking
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Cluster-based eligibility:
  Infrastructure projects are typically approved for:
    - Farmer Producer Organizations (FPOs)
    - Cooperatives
    - Aggregated farmer groups
  Individual farmers may have limited eligibility.

- Project-based approval:
  Infrastructure support requires:
    - detailed project proposal
    - capacity planning
    - location suitability

- Capital-intensive infrastructure:
  Approval depends on feasibility and funding availability.

- Existing facility usage:
  Farmers can also use existing cold storage facilities
  without applying for infrastructure creation.

- Capacity constraint:
  Storage space is limited and must be booked.

- Commodity dependency:
  Storage suitability depends on:
    - crop type (fruits, vegetables, perishables)
    - temperature requirements

- Booking lifecycle:
  booking_requested → confirmed → stored → released

- Usage tracking:
  Storage duration and utilization must be tracked.

- Grievances should ONLY be raised after checking application or booking status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- application_status:
  not_applied → submitted → under_review → approved → rejected

- project_status:
  not_started → in_progress → completed → operational

- facility_status:
  inactive → active → maintenance

- booking_status:
  requested → confirmed → active → completed → cancelled

- capacity_status:
  available → limited → full

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- individual farmer applies where group required
- incomplete or invalid project proposal
- location not suitable for infrastructure
- facility not operational
- storage capacity unavailable
- incorrect crop-storage mismatch
- booking conflict or overbooking
- storage duration exceeded
- infrastructure approval delay
- duplicate booking requests

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (eligibility, capacity, crop compatibility)
- rejection conditions (invalid application, unavailable capacity)
- failure scenarios (booking failure, infrastructure delay)

Tools must NOT assume success-only execution.
