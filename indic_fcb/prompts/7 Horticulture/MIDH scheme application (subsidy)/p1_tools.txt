You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
MIDH (Mission for Integrated Development of Horticulture)
scheme application and subsidy service on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Eligibility checking for horticulture subsidy
- Scheme and component selection (orchard, polyhouse, drip irrigation, etc.)
- Project proposal submission
- Subsidy calculation (based on category, crop, region)
- Application review and approval
- Implementation tracking
- Inspection and verification
- Subsidy disbursement tracking
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Scheme component dependency:
  MIDH includes multiple components such as:
    - orchard development
    - polyhouse / greenhouse
    - drip irrigation
    - nursery development

- Eligibility dependency:
  Farmer must satisfy:
    - land ownership or valid lease
    - crop suitability
    - scheme-specific criteria

- Category-based subsidy:
  Subsidy percentage varies by:
    - farmer category (general, SC/ST, women)
    - region (normal vs special/hilly areas)

- Project requirement:
  Subsidy is provided only for approved projects.

- Implementation dependency:
  Subsidy is released ONLY after:
    - project is implemented
    - assets are created

- Inspection requirement:
  Physical verification is mandatory before subsidy release.

- Duplicate prevention:
  Same project or land cannot be subsidized multiple times.

- Partial subsidy:
  Subsidy may be released in stages based on progress.

- Grievances should ONLY be raised after checking application or subsidy status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- application_status:
  not_applied → submitted → under_review → approved → rejected

- project_status:
  not_started → in_progress → partially_completed → completed → verified

- inspection_status:
  not_scheduled → scheduled → completed → verified → failed

- subsidy_status:
  not_initiated → pending → approved → partially_disbursed → disbursed → failed

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- farmer not eligible but applies
- incorrect or incomplete project proposal
- invalid crop or unsuitable region
- duplicate subsidy application
- mismatch between declared and actual project
- project not implemented after approval
- inspection failure due to incomplete setup
- incorrect subsidy calculation
- delay in subsidy disbursement
- partial completion leading to partial subsidy

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (eligibility, land, crop, project details)
- rejection conditions (invalid application, duplicate project)
- failure scenarios (inspection failure, subsidy delay)

Tools must NOT assume success-only execution.
