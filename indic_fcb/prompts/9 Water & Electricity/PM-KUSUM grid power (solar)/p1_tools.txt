You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
PM-KUSUM (solar grid power / feeder-based solarization)
service on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Applying for solar plant installation (grid-connected)
- Eligibility checking
- Capacity allocation (kW-based)
- Installation tracking
- Energy generation monitoring
- Net metering and grid export tracking
- Revenue / payment tracking for surplus energy
- Maintenance and fault reporting
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Eligibility dependency:
  Farmer must satisfy:
    - land ownership or lease
    - grid connectivity availability
    - scheme-specific eligibility

- Capacity constraint:
  Solar capacity is limited by:
    - land size
    - feeder capacity
    - regulatory caps (kW limits)

- Grid dependency:
  System requires:
    - grid connection
    - DISCOM approval

- Installation dependency:
  System must be installed and verified before energy generation.

- Energy generation lifecycle:
  installed → generating → exporting → idle/fault

- Net metering:
  Energy exported to grid is measured and recorded.

- Revenue dependency:
  Payments are based on:
    - units exported
    - tariff rates

- Payment delay:
  Revenue payments may be delayed due to DISCOM processing.

- Maintenance requirement:
  Faults or downtime must be handled.

- No guaranteed revenue:
  Revenue depends on:
    - generation levels
    - grid conditions
    - policy rates

- Grievances should ONLY be raised after checking generation or payment status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- application_status:
  not_applied → submitted → under_review → approved → rejected

- installation_status:
  not_started → in_progress → installed → verified → operational

- generation_status:
  not_generating → generating → exporting → idle → fault

- payment_status:
  not_initiated → pending → processed → credited → failed

- grid_status:
  not_connected → connected → active → disrupted

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- farmer not eligible but applies
- grid not available in area
- capacity exceeds allowed limits
- installation delay or failure
- system installed but not generating
- incorrect net metering readings
- low or zero generation due to weather
- payment not received or delayed
- mismatch in exported units vs recorded units
- system fault or downtime

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (eligibility, grid connectivity, capacity limits)

- failure scenarios (installation delay, payment failure, system fault)
