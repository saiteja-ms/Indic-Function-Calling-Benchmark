You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
Agri Marketing (buy-sell platform for farmers/FPOs)
service on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer, buyer, and FPO interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer/FPO authentication
- Creating and managing crop listings
- Searching and browsing listings
- Price discovery and comparison
- Placing and managing orders
- Bid-based (auction) participation
- Order fulfillment and delivery tracking
- Payment processing and tracking
- Cancellation and refund handling
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED for all transactional actions:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Role distinction:
  Users can act as:
    - seller (farmer/FPO)
    - buyer (trader/consumer)

- Listing ownership:
  Only the creator of a listing can modify or delete it.

- Commodity standardization:
  Listings must include:
    - commodity
    - quality grade
    - quantity
    - unit

- Pricing model:
  Listings can be:
    - fixed price
    - auction-based

- Order lifecycle:
  Orders must follow strict states:
    created → confirmed → dispatched → delivered → completed

- Payment dependency:
  Payment must be successful before order completion.

- Logistics constraint:
  Delivery tracking exists only after dispatch.

- Cancellation rules:
  Orders cannot be cancelled after dispatch.

- Partial fulfillment:
  Large orders may be partially fulfilled.

- Grievances should ONLY be raised after checking order/payment status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- listing_status:
  active → updated → inactive → deleted

- order_status:
  created → confirmed → dispatched → delivered → completed → cancelled

- payment_status:
  pending → paid → failed → refunded

- auction_status:
  open → bidding → closed → awarded

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- duplicate listing creation
- invalid commodity or unsupported crop
- insufficient quantity for order
- placing order on inactive listing
- bid lower than minimum price
- multiple buyers bidding simultaneously
- order cancellation after dispatch attempt
- payment failure or timeout
- delivery delay or mismatch
- partial delivery
- fraudulent or incorrect listing

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (quantity, price, listing status)
- rejection conditions (invalid order, unauthorized modification)
- failure scenarios (payment failure, delivery issues)

Tools must NOT assume success-only execution.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- farmer creating and managing listings
- buyer searching and placing orders
- auction participation and bidding
- successful order lifecycle
- failed order/payment scenarios
- delivery tracking and disputes
- grievance escalation

---

## TOOL DESIGN REQUIREMENTS

- Naming format: agrimarket_verb_noun (lowercase, underscores only)
- Each tool must represent ONE atomic API
- Tools should be independent (no chaining logic required)
