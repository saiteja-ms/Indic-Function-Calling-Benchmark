You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
MSP Procurement (Minimum Support Price government procurement)
service on the UMANG app.

The number of tools should be sufficient (typically 10–14 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Farmer registration for MSP procurement
- Crop declaration for a procurement season
- Token generation for mandi visit
- Checking MSP rates for crops
- Scheduling procurement slot
- Delivering produce at mandi
- Quality inspection and grading
- Procurement acceptance/rejection
- Payment processing and tracking
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED for all procurement actions:
  Aadhaar + OTP verification must be completed first.
  Authentication returns a session_token.

- Farmer registration is MANDATORY:
  Only registered farmers can participate in MSP procurement.

- Crop declaration is REQUIRED before procurement:
  Farmer must declare crop and expected quantity for the season.

- MSP rates are FIXED by government:
  Farmers cannot negotiate MSP prices.

- Procurement is mandi-based:
  Produce must be delivered to a registered procurement center.

- Token system:
  Farmers must obtain a procurement token before visiting mandi.

- Quality check is STRICT:
  Produce must meet Fair Average Quality (FAQ) standards.
  Substandard produce is rejected.

- Payment is post-procurement:
  Payment is processed only after successful acceptance of produce.

- State-specific rules:
  Procurement policies may vary across states.

- Grievances should ONLY be raised after checking procurement/payment status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- registration_status:
  unregistered → registered

- procurement_status:
  not_declared → declared → scheduled → delivered → inspected → accepted/rejected → payment_processed

- payment_status:
  pending → initiated → completed → failed

Tools must clearly define:
- when they are valid to call
- when they are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- farmer is not registered
- crop not declared but trying to schedule
- invalid crop or unsupported commodity
- exceeding declared quantity
- duplicate token requests
- poor quality produce rejection
- payment delays or failures
- wrong mandi selection
- expired procurement window

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (e.g., crop must be declared before scheduling)
- rejection conditions (e.g., quality below FAQ)
- failure scenarios (e.g., payment processing failure)

Tools must NOT assume success-only execution.

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- new farmer onboarding

- rejected procurement flow
- delayed payment scenario
- grievance escalation scenario
