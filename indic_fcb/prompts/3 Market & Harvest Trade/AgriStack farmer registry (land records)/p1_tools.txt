You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
AgriStack Farmer Registry (digital farmer identity and land records)
service on the UMANG app.

The number of tools should be sufficient (typically 10–14 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Farmer profile registration and retrieval
- Land parcel linking and registration
- Fetching land records from state databases
- Ownership verification
- Crop declaration per land parcel
- Updating farmer profile details
- Consent-based data sharing
- Registry status tracking
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED for all personal data access:
  Aadhaar + OTP verification must be completed first.
  Authentication returns a session_token.

- Aadhaar uniqueness:
  Each Aadhaar can have ONLY one farmer registry profile.
  Duplicate registrations must be rejected.

- Land ownership verification:
  Land parcels must be verified against state land records.
  Unverified or self-declared land is not valid for scheme usage.

- One-to-many mapping:
  A farmer can own multiple land parcels.

- State integration dependency:
  Land records are fetched from state systems (e.g., Bhulekh).
  Data availability may vary across states.

- Immutable government records:
  Verified land ownership data cannot be edited directly.

- Crop declaration dependency:
  Crops must be declared per land parcel, not globally.

- Consent-based sharing:
  Farmer must explicitly grant permission before sharing data with other services.

- Grievances should ONLY be raised after checking registry or land status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- profile_status:
  not_registered → registered → verified

- land_record_status:
  unverified → pending_verification → verified → rejected

- consent_status:
  not_given → granted → revoked

Tools must clearly define:
- when they are valid to call
- when they are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- duplicate Aadhaar registration attempt
- land parcel not found in state records
- mismatched ownership (Aadhaar does not match land owner)
- multiple land parcels with partial verification
- attempting crop declaration on unverified land
- state system unavailable or delayed response
- invalid land parcel ID
- missing consent for data sharing

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (Aadhaar format, land ID validity)
- rejection conditions (duplicate profile, invalid ownership)
- failure scenarios (state API unavailable, verification delay)

Tools must NOT assume success-only execution.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- new farmer registration
- existing farmer retrieving profile
- linking multiple land parcels
- land verification success/failure
- crop declaration scenarios
- consent granting and revocation
- grievance escalation

---
