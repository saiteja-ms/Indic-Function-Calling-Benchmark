You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
e-Pashu Haat (online livestock marketplace for buying and selling cattle)
service on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic buyer/seller interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- User authentication
- Registering livestock for sale
- Searching livestock listings
- Filtering by breed, location, price, and purpose
- Viewing detailed livestock information
- Verifying animal health and certification
- Placing purchase requests
- Negotiation or bid-based interactions
- Order confirmation and ownership transfer
- Logistics and transport coordination
- Payment tracking
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED for transactional actions:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Role distinction:
  Users can act as:
    - seller (livestock owner)
    - buyer (farmer/trader)

- Livestock registration requirement:
  Animals must be registered with:
    - breed
    - age
    - health status
    - vaccination records

- Certification dependency:
  Verified listings may include:
    - breed certification
    - health certificate

- Listing ownership:
  Only the seller can modify or delete their listing.

- Animal uniqueness:
  Each livestock_id must represent a unique animal.

- Price and negotiation:
  Listings may support:
    - fixed price
    - negotiable price

- Order lifecycle:
  purchase_requested → confirmed → payment_done → ownership_transferred

- Ownership transfer:
  Ownership must be updated after successful transaction.

- Logistics dependency:
  Transport coordination is required post-purchase.

- No illegal trade:
  Unverified or restricted animals must not be listed.

- Grievances should ONLY be raised after checking transaction status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- listing_status:
  active → updated → inactive → deleted

- order_status:
  requested → confirmed → payment_done → transferred → completed → cancelled

- verification_status:
  unverified → verified → rejected

- logistics_status:
  not_started → arranged → in_transit → delivered

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- unregistered livestock listed
- invalid or incomplete livestock details
- duplicate livestock listing
- unverified or fake certification
- buyer attempts purchase on inactive listing
- conflicting or ambiguous listings
- negotiation conflicts
- payment failure
- logistics delay or failure
- ownership transfer not completed
- fraudulent listing or misleading data

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (livestock registration, certification, ownership)
- rejection conditions (invalid listing, unauthorized modification)
- failure scenarios (payment failure, logistics delay)

Tools must NOT assume success-only execution.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- seller listing livestock

- verifying animal details
- initiating and completing purchase
- ownership transfer
- logistics tracking
- failure or dispute scenarios
- grievance escalation
