You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
NABARD Livestock Loan (credit support for dairy, poultry, and allied activities)
service on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Loan eligibility checking
- Credit scoring and assessment
- Loan application submission
- Document verification
- Loan approval or rejection
- Loan disbursement tracking
- EMI and repayment tracking
- Default handling and restructuring
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Credit eligibility:
  Loan approval depends on:
    - credit history
    - repayment capacity
    - project feasibility

- Bank dependency:
  Loan processing is handled by banks/NBFCs supported by NABARD.

- Project linkage:
  Loan must be tied to a valid livestock project:
    - dairy
    - poultry
    - goat/sheep rearing

- Document verification:
  Required documents may include:
    - identity proof
    - land records
    - project proposal

- Loan approval is NOT guaranteed:
  Applications may be rejected based on risk assessment.

- Disbursement dependency:
  Loan is disbursed only after approval and verification.

- Repayment lifecycle:
  Borrower must repay via scheduled EMIs.

- Default handling:
  Non-payment may lead to:
    - penalty
    - restructuring
    - recovery action

- No direct subsidy:
  This is a credit product, not a direct subsidy (unless linked separately).

- Grievances should ONLY be raised after checking loan or repayment status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- application_status:
  not_applied → submitted → under_review → approved → rejected

- verification_status:
  not_started → in_progress → verified → failed

- loan_status:
  not_sanctioned → sanctioned → disbursed → active → closed → defaulted

- repayment_status:
  not_started → ongoing → overdue → completed

- disbursement_status:
  not_initiated → initiated → completed → failed

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- farmer not eligible but applies
- incomplete or invalid documentation
- poor credit history leading to rejection
- mismatch between project and loan purpose
- loan approved but not disbursed
- delayed disbursement
- EMI not paid leading to overdue/default
- incorrect repayment schedule
- loan closure issues
- multiple loan applications causing conflict

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (eligibility, documentation, project linkage)
- rejection conditions (credit risk, invalid application)
- failure scenarios (verification failure, disbursement delay, default)

Tools must NOT assume success-only execution.
