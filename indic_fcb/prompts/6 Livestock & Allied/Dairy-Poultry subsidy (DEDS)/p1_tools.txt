You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
Dairy Entrepreneurship Development Scheme (DEDS) /
Poultry subsidy service on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Eligibility checking for subsidy
- Project proposal submission (dairy/poultry unit)
- Loan application through bank
- Subsidy calculation (credit-linked)
- Loan approval and subsidy linkage
- Asset creation tracking (shed, livestock, equipment)
- Inspection and utilization verification
- Subsidy disbursement tracking
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Credit-linked subsidy:
  Subsidy is provided ONLY if:
    - loan is approved by bank
    - project is implemented

- Bank dependency:
  Loan approval is handled by bank or financial institution.

- Project requirement:
  Farmer must submit a detailed project proposal
  (e.g., dairy unit, poultry farm).

- Asset creation dependency:
  Subsidy is released ONLY after:
    - physical assets are created
    - project is operational

- Inspection requirement:
  Government authority must verify project implementation.

- Subsidy structure:
  Subsidy is a percentage of project cost and varies by category.

- Duplicate prevention:
  Same farmer cannot claim subsidy multiple times for same project.

- Category-based eligibility:
  Subsidy percentage may differ for:
    - general
    - SC/ST
    - women farmers

- Grievances should ONLY be raised after checking application or subsidy status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- application_status:
  not_applied → submitted → under_review → approved → rejected

- loan_status:
  not_applied → applied → sanctioned → rejected → disbursed

- project_status:
  not_started → in_progress → completed → verified

- subsidy_status:
  not_initiated → pending → approved → disbursed → failed

- inspection_status:
  not_scheduled → scheduled → completed → verified

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- farmer not eligible but applies
- incomplete or invalid project proposal
- loan rejected by bank
- mismatch between project and subsidy criteria
- project not implemented after loan sanction
- inspection failure due to incomplete setup
- duplicate subsidy application
- incorrect category declaration
- subsidy calculation mismatch
- subsidy disbursement delay or failure

Descriptions must explicitly reflect these cases.
