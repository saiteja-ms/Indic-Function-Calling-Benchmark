You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
SMAM (Sub-Mission on Agricultural Mechanization)
subsidy service for farm machinery (tractor, harvester, implements)
on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Eligibility checking for machinery subsidy
- Machinery selection (tractor, harvester, etc.)
- Vendor selection
- Subsidy calculation
- Application submission
- Purchase validation
- Inspection and verification
- Subsidy disbursement tracking
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Eligibility dependency:
  Farmer must satisfy:
    - land ownership or operational holding
    - category eligibility (general, SC/ST, women)
    - scheme-specific criteria

- Machinery dependency:
  Subsidy applies ONLY to approved machinery types:
    - tractor
    - harvester
    - power tiller
    - implements

- Vendor dependency:
  Machinery must be purchased from:
    - authorized vendors

- Purchase requirement:
  Subsidy is linked to:
    - actual purchase
    - valid invoice

- Subsidy structure:
  Subsidy is a percentage of machinery cost,
  varying by category and region.

- Duplicate prevention:
  Same farmer cannot claim subsidy multiple times
  for the same machinery category within a defined period.

- Inspection requirement:
  Physical verification of machinery is required.

- Disbursement dependency:
  Subsidy is released ONLY after:
    - purchase verification
    - inspection approval

- Partial subsidy:
  Subsidy may have upper limits (capped amount).

- Grievances should ONLY be raised after checking application or subsidy status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- application_status:
  not_applied → submitted → under_review → approved → rejected

- purchase_status:
  not_initiated → initiated → completed → verified

- inspection_status:
  not_scheduled → scheduled → completed → verified → failed

- subsidy_status:
  not_initiated → pending → approved → disbursed → failed

- vendor_status:
  not_selected → selected → validated

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- farmer not eligible but applies
- invalid or unsupported machinery selected
- vendor not authorized
- purchase not completed after approval
- mismatch between invoice and application
- duplicate subsidy attempt
- incorrect category declaration
- inspection failure due to missing or incorrect machinery
- subsidy calculation mismatch
- delay or failure in subsidy disbursement

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (eligibility, vendor, machinery type)
- rejection conditions (invalid application, duplicate claim)
- failure scenarios (inspection failure, subsidy delay)

Tools must NOT assume success-only execution.
