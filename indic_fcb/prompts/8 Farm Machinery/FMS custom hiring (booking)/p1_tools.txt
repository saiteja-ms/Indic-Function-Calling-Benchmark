You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
FMS (Farm Machinery Service / Custom Hiring Service)
booking system on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Discovering available farm services (ploughing, harvesting, spraying, etc.)
- Searching service providers
- Checking service availability
- Booking service (not just machinery)
- Scheduling job execution
- Tracking service progress
- Completion verification
- Payment tracking
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Public vs authenticated access:
  - Service browsing is PUBLIC
  - Booking requires authentication

- Service-based model:
  Farmers are booking:
    - service + machine + operator
  NOT just equipment rental.

- Location dependency:
  Service availability depends on:
    - service provider location
    - travel feasibility

- Task-based pricing:
  Pricing may depend on:
    - land area (acre/hectare)
    - duration
    - type of operation

- Scheduling dependency:
  Service must be booked for:
    - specific date
    - estimated duration

- Provider assignment:
  Service provider must be assigned before execution.

- Execution lifecycle:
  booking_requested → confirmed → assigned → in_progress → completed → verified

- Completion verification:
  Service must be verified before final closure.

- Payment dependency:
  Payment may be:
    - advance
    - post-service

- No guaranteed availability:
  Service may not be available due to:
    - high demand
    - weather conditions
    - provider constraints

- Grievances should ONLY be raised after checking service status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- booking_status:
  requested → confirmed → assigned → in_progress → completed → verified → cancelled → failed

- service_status:
  not_started → scheduled → in_progress → completed

- provider_status:
  available → assigned → busy → unavailable

- payment_status:
  not_initiated → pending → completed → failed

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- no service providers available in location
- service requested outside feasible area
- invalid or unrealistic land area
- scheduling conflict
- provider unavailable after booking
- weather disruption
- service not completed properly
- incorrect service execution
- payment failure
- duplicate booking attempts

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (location, feasibility, scheduling)
- rejection conditions (invalid request, no provider)
- failure scenarios (provider failure, incomplete service)

Tools must NOT assume success-only execution.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- farmer discovering services
- checking availability
- booking service
- tracking execution
- verifying completion
- handling failed or incomplete services
- grievance escalation

---

## TOOL DESIGN REQUIREMENTS

- Naming format: fms_verb_noun (lowercase, underscores only)
- Each tool must represent ONE atomic API
- Tools should be independent (no chaining logic required)
