You are building a function-calling benchmark dataset in the style
of the Berkeley Function Calling Leaderboard (BFCL).

Your task: Generate a JSON array of tool schemas for the
iFMS (Integrated Fertilizer Management System - fertilizer subsidy DBT)
service on the UMANG app.

The number of tools should be sufficient (typically 12–16 tools)
to cover all realistic farmer interactions and edge cases.

---

## CORE OBJECTIVE

Design tools that enable realistic workflows such as:
- Farmer authentication
- Checking subsidy eligibility
- Fertilizer availability lookup
- Retailer/point-of-sale identification
- Purchase transaction recording
- Subsidy calculation and application
- Transaction validation (Aadhaar-based)
- Subsidy disbursement tracking
- Purchase history retrieval
- Grievance handling

---

## CRITICAL DOMAIN CONSTRAINTS (MUST BE ENCODED IN DESCRIPTIONS)

- Authentication is REQUIRED:
  Aadhaar + OTP verification must be completed.
  Authentication returns a session_token.

- Aadhaar-linked purchase:
  Fertilizer purchase must be authenticated using Aadhaar at POS.

- Subsidy is purchase-linked:
  Subsidy is applied ONLY when:
    - fertilizer is purchased from authorized retailer
    - transaction is recorded in system

- Retailer dependency:
  Purchase must occur through registered fertilizer dealers.

- Subsidy type:
  Subsidy is provided directly to fertilizer companies,
  not as direct cash transfer to farmer (price is reduced upfront).

- Quantity limits:
  Subsidy may be limited based on:
    - crop type
    - land size
    - season

- Inventory dependency:
  Fertilizer availability depends on stock at retailer.

- Duplicate transaction prevention:
  Same purchase cannot be recorded multiple times.

- Grievances should ONLY be raised after checking transaction or subsidy status.

---

## STATE TRANSITION REQUIREMENT (MANDATORY)

Tool descriptions MUST encode valid state transitions:

- transaction_status:
  initiated → validated → completed → failed

- subsidy_status:
  not_applied → applied → verified → settled

- inventory_status:
  available → low_stock → out_of_stock

- purchase_status:
  not_recorded → recorded → verified

Tools must define:
- when actions are valid
- when actions are invalid

---

## EDGE CASE REQUIREMENT (MANDATORY)

The toolset MUST support scenarios where:
- farmer not eligible but attempts purchase subsidy
- invalid Aadhaar authentication at POS
- purchase from unauthorized retailer
- insufficient stock at retailer
- exceeding subsidy quantity limits
- duplicate transaction attempt
- mismatch between land/crop and fertilizer usage
- transaction failure at POS
- subsidy calculation mismatch
- delayed or missing subsidy application

Descriptions must explicitly reflect these cases.

---

## ERROR HANDLING REQUIREMENT (MANDATORY)

Each tool description MUST include:
- validation rules (Aadhaar, retailer validity, quantity limits)
- rejection conditions (invalid purchase, ineligible farmer)
- failure scenarios (transaction failure, subsidy mismatch)

Tools must NOT assume success-only execution.

---

## SCENARIO COVERAGE REQUIREMENT (MANDATORY)

The toolset MUST support:
- farmer checking fertilizer availability
- purchasing fertilizer with subsidy
- validating transaction
- tracking subsidy application
- retrieving purchase history
- handling failed or invalid transactions
- grievance escalation
