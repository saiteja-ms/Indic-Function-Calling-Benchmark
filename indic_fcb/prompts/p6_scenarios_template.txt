SECTION 1 — CORE PRINCIPLE

A scenario has FOUR parts:
  1. initial_state — what the stub is seeded with
  2. conversation — alternating user and ground_truth
  3. axes — DERIVED from the conversation structure
  4. expected_final_state — only changed fields

The intent defines the GOAL and the STATE.
The archetype defines the CONVERSATION SHAPE.
The conversation shape determines the AXES.

SECTION 2 — STRUCTURAL AXIS DEFINITIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These definitions are STRUCTURAL — derived from
the actual conversation you generate, not from
labels.

AXIS 1 — conversation_length:
  single_turn = exactly ONE user message in the
                conversation
  multi_turn  = TWO OR MORE user messages

AXIS 2 — tool_calls_per_turn:
  single_step = every ground_truth turn has at
                most ONE tool_call
  multi_step  = at least one ground_truth turn
                has TWO or more tool_calls

AXIS 3 — task_type:
  irrelevance       = ALL ground_truth turns have
                      null_call: true AND at least
                      one has irrelevance_reason
  parallel_multiple = at least one ground_truth
                      turn has multiple tool_calls
                      AND those calls target
                      DIFFERENT tool_names
  simple            = anything else (including
                      parallel calls to the SAME
                      tool — that is "simple"
                      under task_type because the
                      multi-step nature is captured
                      by AXIS 2)

SECTION 3 — CONVERSATION SHAPE (DRIVEN BY ARCHETYPE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The archetype's INFORMATION_DISCLOSURE attribute
controls how many user turns the conversation has.

upfront_complete:
  Single user turn containing every parameter.
  Even for "miss_param" or "base" category intents,
  this archetype gives everything in one message.
  HOWEVER, base chains still need multi-turn because
  the chain order forces it.

partial_then_supply:
  Two user turns: first turn describes the problem
  with some identifiers, second turn provides the
  rest after the model asks.

reactive_only:
  Three or more user turns: each parameter comes
  in a separate user message after explicit ask.

SECTION 4 — TURN STRUCTURE (STRICT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Each turn has TWO entries with the SAME turn_index:
  - speaker: user
  - speaker: ground_truth

Turn pattern:
  turn 1:
    {speaker: "user",         turn_index: 1, ...}
    {speaker: "ground_truth", turn_index: 1, ...}
  turn 2:
    {speaker: "user",         turn_index: 2, ...}
    {speaker: "ground_truth", turn_index: 2, ...}

Ground truth is what the model SHOULD do AFTER
reading that turn's user message.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SECTION 5 — GROUND TRUTH PER CATEGORY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

simple: one user turn, one tool call.
multiple: one tool call. Distractors must NOT
  appear in ground_truth.
parallel: one turn with multiple calls to the
  SAME tool, different parameters.
parallel_multiple: one turn with multiple calls
  to DIFFERENT tools, no inter-call dependency.
task_irrelevance: every turn has null_call: true
  and irrelevance_reason set.
base: multi-turn chain, one tool call per turn,
  order enforced.
miss_param: one turn has null_call: true with
  model_should_ask_for set. Next turn provides
  the parameter and ground_truth makes the call.
miss_func: one turn has null_call: true with
  model_should_decline set.
long_context: base chain plus 3-5 padding user
  turns BEFORE the chain begins. Padding turns
  have tool_calls: [] and null_call: true.

SECTION 6 — eval_mode SELECTION (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Every parameter has an eval_mode. Three options:

  EXACT
    Structured identifiers: aadhaar_number,
    mobile_number, otp, dates, amounts, enum
    values, booleans, and all _id / _number /
    _code fields stated by the user.

  SUBSTRING
    Free-text only: complaint_description,
    grievance_remarks, address_details,
    resolution_notes.

  TYPE_ONLY
    ONLY for values returned by a prior tool
    call within this same conversation.
    Legitimate uses:
      session_token (returned by authenticate)
      grievance_id RETURNED by raise_grievance
      application_id RETURNED by submit_application

DECISION FLOW:

  Step 1: Does the value appear in any user
          message in this conversation?
          YES → cannot be TYPE_ONLY. Go to Step 3.
          NO  → Go to Step 2.

  Step 2: Was the value returned by a prior
          tool call within this conversation?
          YES → TYPE_ONLY
          NO  → ERROR. Re-examine the scenario.

  Step 3: Is the field a structured identifier?
          YES → EXACT
          NO  → SUBSTRING (free-text only)

SECTION 7 — AXES DERIVATION (NEVER COPY FROM INTENT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

axes is DERIVED from the conversation you
generated using the STRUCTURAL DEFINITIONS in
Section 2. Do NOT copy from the intent — the
intent's axes assume an upfront_complete
archetype, but partial_then_supply and
reactive_only archetypes change the actual
structure.

ALGORITHM:

  conversation_length:
    Count distinct turn_index values where
    speaker == "user".
    1 → single_turn
    2+ → multi_turn

  tool_calls_per_turn:
    Find max(len(tool_calls)) across all
    ground_truth turns.
    >1 → multi_step
    Else → single_step

  task_type:
    If ALL ground_truth turns have null_call:
       true AND at least one has
       irrelevance_reason:
         "irrelevance"
    Else if max tool_calls > 1 AND those calls
         target DIFFERENT tool_names:
         "parallel_multiple"
    Else:
         "simple"
